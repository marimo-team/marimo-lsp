From scattered effects to owned causality.

The stack is not mainly a reducer refactor. It is an attempt to make one module own the meaning, ordering, and presentation of a cell run. That buys real leverage—but two causal facts are still sampled too late or discarded too early.

Conceptual delta

First understand what knowledge moves. The details of Effect, tagged enums, and maps are secondary.

The old architecture knew the same story in several places.

A kernel cell-op updated reducer state, produced actions, mutated a VS Code execution, and separately updated staleness bookkeeping. Correctness depended on the caller invoking those pieces in the right order with live editor objects.

→

// Public side doors mutate related truth:

The Interface exposes several operations whose ordering and shared invariants callers must understand.
AFTER · FACTS ENTER ONE INTERFACE

  CellInput.Operation({
    notebookId,
    operation,
    source,
    drive,
  }),
);

// Lifecycle uses the same ordering lane:
accept(CellInput.CellsRemoved({ ... }));
accept(CellInput.Invalidated({ ... }));
The Interface becomes event-shaped: callers report facts; the Module owns their ordering and consequences.
Four commits, one arc

Each PR removes one category of knowledge from callers or from the host-specific Implementation.

The stack deepens one layer at a time.

Read these as a progression, not four isolated refactors. The later PRs make the architectural intent of the earlier ones visible.

#756

Put accepted source beside cell-run state.

Deletes the parallel lastExecutedCodeRef. Queueing and invalidation now change the same state record that owns phase and runtime state.

Removed knowledge

Callers no longer coordinate RecordExecution and InvalidateCell actions.

Leverage gained

One transition describes both execution phase and staleness truth.

#757

Give every run command an identity.

OpenRun, StartRun, RenderOutputs, and CloseRun name the run they intend to touch. Late commands can be rejected by an Adapter.

Removed knowledge

The interpreter no longer assumes “whatever VS Code execution exists” is the intended one.

Leverage gained

Commands become idempotent-ish and stale presentation work can be skipped.

#758

Move VS Code resources behind a Drive Adapter.

CellExecutions stops holding NotebookCellExecution, output projection, and diagnostics. It emits host commands through one effectful capability.

Removed knowledge

The cell-run Module no longer knows VS Code handles, editors, diagnostics, or output projection.

Leverage gained

The state machine is testable with a function; host resource cleanup has one home.

#759

Own cell state and lifecycle by notebook.

Operations, interrupts, cell removal, and notebook invalidation enter a single Interface. Each notebook receives one serialization lane.

Removed knowledge

Callers no longer choose among five mutation methods or clean records independently.

Leverage gained

Removal and reopening can be ordered against in-flight commands without blocking other notebooks.

The shortest honest explanation

          
The stack changes who is responsible for knowing the story of a run.

          
Before, several callers and mutable stores collectively maintained that story. After, callers report facts, CellExecutions turns them into ordered commands, and VsCodeCellDrive presents them.

          
That is worth doing. But “accepted source” and “run-addressed” are only true when provenance and correlation survive end to end.
